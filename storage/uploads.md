# Private file uploads and downloads

Read this when changing file operations or delivery. For bucket, credential, and CORS setup, see [README.md](README.md).

## Upload lifecycle

The protected `/files` example uses a prepare/upload/confirm flow:

1. The route validates the filename, content type, and size, creates organization-scoped `pending`
   metadata, and returns a five-minute presigned POST.
2. The browser uploads directly to S3. File bytes never pass through the web process.
3. The route confirms the object with `HeadObject` and marks it `ready` only when its metadata
   matches.
4. A delayed worker job marks the upload `failed` and removes its object if it is still pending
   after 30 minutes.
5. Downloads re-check organization ownership and redirect to a short-lived signed attachment URL.

Object keys are always generated by the server. Never accept a bucket key or `organizationId` from
the browser. The example limits files to 25 MB and serves them as attachments rather than inline
content. Provider configuration lives in [README.md](README.md).

The signing client uses the same region, credentials, and path-style setting as the storage client.
It falls back to `S3_ENDPOINT` when `S3_PUBLIC_ENDPOINT` is absent. URLs are signed for their final
endpoint; never rewrite them after signing.

## Delivery and CloudFront

The default private-file flow authorizes every download in the app and redirects to a five-minute
S3 signed URL with an attachment disposition. This is the simplest solid default.

For high-volume delivery, put CloudFront in front of the private bucket with Origin Access Control
and issue CloudFront signed URLs or cookies after the same organization authorization check. Keep
uploads pointed directly at S3; a CDN is a download optimization, not required storage
infrastructure.
